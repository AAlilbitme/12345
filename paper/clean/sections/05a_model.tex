\section{Verification of the Model}\label{sec:verification}

This section does two things. Sec.~\ref{sec:core} describes how the model is built, and
Sec.~\ref{sec:verified} lists what we verified and how. The protocol properties themselves
follow in Secs.~\ref{sec:properties} to~\ref{sec:wormhole}. All listings are verbatim excerpts
of \code{lightning.spthy}; a line \texttt{...} marks elided premises or actions.

\subsection{The Core Model}\label{sec:core}

As stated in Sec.~\ref{sec:method}, the main theory contains both layers, as two groups of rules
that share only the long-term keys and the channel topology.

\subsubsection{Payment Channels}\label{sec:core-channels}
A channel is identified by a fresh pointer \code{ptr} to its founding transaction. Our model
tracks two mirror facts about this channel, \code{StateA} and \code{StateB}, one held by each
party, each carrying the two balances (\code{fA}, \code{fB}), a state index~\code{n}, and that
party's own revocation secret together with the corresponding commitment. The commitment names
the channel, the two parties and the index, and contains the hash of the revocation secret. The
state facts do not store its signatures: these are checked when a state is installed
(\code{Both_States_Committed} for the initial state, \code{Revoke_Old_Secret} for every later
one).

The heart of the model is the \emph{update dance}: commit a new state first, then revoke the old
one. \code{Update_State} samples the next state index and both fresh revocation secrets, reads
the two current mirrors and the new balances from the environment, and produces two pending
mirrors without losing anything: each pending mirror still carries the old state next to the
new, signed one.
\begin{spthy}
rule Update_State:
    let newCommitA = <'commit', ptr, $A, $B, ~n_new, h(~sAnew)>
        newCommitB = <'commit', ptr, $B, $A, ~n_new, h(~sBnew)>
        sigAnew    = sign(newCommitA, ltkA)
        sigBnew    = sign(newCommitB, ltkB)
    in
    [ ...
      StateA($A, $B, ptr, n_old, sAold, oldCommitA, fA, fB),
      StateB($A, $B, ptr, n_old, sBold, oldCommitB, fA, fB),
      In(<fA_new, fB_new>) ]
    --[ NewStateBuilt($A, $B, ptr, ~n_new, fA_new, fB_new) ]->
    [ PendingA($A, $B, ptr, n_old, sAold, oldCommitA,
               ~n_new, ~sAnew, newCommitA, sigAnew, fA_new, fB_new),
      PendingB($A, $B, ptr, n_old, sBold, oldCommitB,
               ~n_new, ~sBnew, newCommitB, sigBnew, fA_new, fB_new) ]
\end{spthy}
Only afterwards does \code{Revoke_Old_Secret} supersede the old state: it consumes the two
pending mirrors, installs them as the new state, and, crucially, records the old revocation
secrets as persistent facts.
\begin{spthy}
rule Revoke_Old_Secret:
    [ PendingA($A, $B, ptr, n_old, sAold, oldCommitA,
               n_new, sAnew, newCommitA, sigAnew, fA_new, fB_new),
      PendingB($A, $B, ptr, n_old, sBold, oldCommitB,
               n_new, sBnew, newCommitB, sigBnew, fA_new, fB_new),
      !Pk($A, pkA), !Pk($B, pkB) ]
    --[ StateUpdate($A, $B, ptr, n_new),
        Revoke($A, n_old, sAold),
        Revoke($B, n_old, sBold),
        Eq(verify(sigAnew, newCommitA, pkA), true),
        Eq(verify(sigBnew, newCommitB, pkB), true) ]->
    [ StateA($A, $B, ptr, n_new, sAnew, newCommitA, fA_new, fB_new),
      StateB($A, $B, ptr, n_new, sBnew, newCommitB, fA_new, fB_new),
      !RevokedSecret($A, n_old, sAold, oldCommitA),
      !RevokedSecret($B, n_old, sBold, oldCommitB),
      RevokedCommitmentUnspent(ptr, $A, $B, n_old, oldCommitA),
      RevokedCommitmentUnspent(ptr, $B, $A, n_old, oldCommitB) ]
\end{spthy}
Two details deserve emphasis. First, the signature checks of Sec.~\ref{sec:protocol} become the
two \code{Eq} action facts. A \tamarin{} rule cannot fail, so restriction \code{Equality} turns
these action facts into hard prerequisites: the rule fires only if both new commitments carry
valid signatures under the parties' public keys. Second, the old revocation secret becomes
persistent knowledge (\code{!RevokedSecret}), while the old commitment's spend becomes a linear
one-shot token (\code{RevokedCommitmentUnspent}). This keeps the secret available for later
punishment while guaranteeing that a given revoked commitment is spent at most once, following
the single-spend discipline of Sec.~\ref{par:single-spend}. The order (commit, then revoke) is
what protects a party that aborts mid-update: the old state is never revoked until a fully
signed new one exists.

The remaining phases reuse the same facts, so we give only the closing path here and trust the
pattern carries over. \code{Lock_Funds_And_Open} mints the two mirrors together with the
persistent facts \code{!ValidOnChain(ptr)}, \code{!ChannelRecord(ptr,$A,$B)} and
\code{!ChannelConnect} (one per direction), and the per-channel slot \code{Mutex(ptr)}, which
the routing rules take and give back (Sec.~\ref{sec:core-routing}). A unilateral close spends
the current mirror: \code{Publish_Current_A} turns \code{StateA} into an \code{OnChainDelayed}
and an \code{OnChainInstant} output,
\begin{spthy}
rule Publish_Current_A:
    [ StateA($A, $B, ptr, n, sA, commitA, fA, fB), !ValidOnChain(ptr) ]
    --[ Publish($A, n, commitA),
        ...
        OnChainInstantProduce($B, n) ]->
    [ OnChainDelayed($A, n, commitA),
      OnChainInstant($B, n, commitA) ]
\end{spthy}
and \code{Claim_Funds_A} later releases the delayed output to its owner:
\begin{spthy}
rule Claim_Funds_A:
    [ OnChainDelayed($A, n, txContent) ]
    --[ ClaimFunds($A, n), CSVPassed($A, n), SettledTx($A, txContent) ]->
    [ FundsTo($A, n) ]
\end{spthy}
Notably, the \code{CSVPassed} action lets us capture that time has passed. A cooperative close
(\code{Honest_Close}) signs one shared settlement transaction instead, and punishment
(\code{Publish_Revoked_A} consuming \code{RevokedCommitmentUnspent}, then \code{Punish_A})
transfers the whole channel to the honest party.

\subsubsection{Routing}\label{sec:core-routing}
The routing layer of Sec.~\ref{sec:routing} is a chain of HTLC offers in the forward direction
and of fulfilments in the backward one, and our model gives each direction its own fact. Forward
obligations travel as linear facts \code{Route($Prev,$Me,ptrIn,y)}, and every added HTLC is also
recorded in a persistent fact \code{!RouteInfo}. Once an HTLC is redeemed, the preimage travels
back as \code{Fulfilled(ptr,x)}. The slot \code{Mutex(ptr)}, minted when the channel opens
(Sec.~\ref{sec:core-channels}), acts as a per-channel lock: it is consumed whenever an HTLC is
added to the channel and given back when that HTLC is redeemed or refunded. Hence no two HTLCs
are pending on the same channel at the same time, while the channel stays reusable for later
payments.

The core of the model is the generic forwarding rule, one rule for any number of hops.
\begin{spthy}
rule Forward_HTLC:
    [ Route($Prev, $Me, ptrIn, y),
      !ChannelConnect(ptrOut, $Me, $Next),
      Mutex(ptrOut),
      In(%vIn), In(%fee), In(%vOut) ]
    --[ HTLCForwarded($Me, $Prev, $Next, ptrIn, ptrOut, y),
        HTLCAdded(ptrOut, y),
        FeeCharged($Me, y, %fee),
        Eq(%vIn,  %vOut %+ %fee),
        Neq(ptrIn, ptrOut), Neq($Prev, $Me), Neq($Me, $Next) ]->
    [ IntermediaryPending($Me, $Prev, $Next, ptrIn, ptrOut, y, %vIn, %vOut, %fee),
      Route($Me, $Next, ptrOut, y),
      !RouteInfo($Me, $Next, ptrOut, y) ]
\end{spthy}
\code{Forward_HTLC} consumes \code{Route($Prev,$Me,ptrIn,y)} and produces
\code{Route($Me,$Next,ptrOut,y)}. It advances the payment one hop, takes the slot
\code{Mutex(ptrOut)} of the outgoing channel, and stores in \code{IntermediaryPending}
everything the hop needs to settle or to be refunded later. \code{$Next} is any party with which
\code{$Me} shares a channel, so routes are built hop by hop and have no fixed length; this
single rule serves every forwarding hop of every route. The incoming amount, the fee and the
outgoing amount are chosen by the environment, constrained only by the \code{Eq} action fact:
the incoming amount is the outgoing amount plus the fee (Sec.~\ref{sec:core-amounts}). The
action \code{HTLCForwarded} identifies the hop in our lemmas, \code{HTLCAdded} feeds
restriction \code{OneHTLCPerHashPerChannel}, and \code{FeeCharged} records the fee the hop
expects. The \code{Neq} facts make the forwarder distinct from both of its neighbours and the
two channels distinct from each other.

The settle round runs in the other direction on separate facts. \code{Receiver_Create_Invoice}
signs a tagged invoice that names the receiver, the sender and the payment hash $y = h(x)$ of a
fresh preimage~$x$, sends it with its signature, and keeps $x$ private in \code{ReceiverInv}.
\code{Sender_Offer_HTLC} checks that signature before offering the first HTLC.
\code{Receiver_Fulfill_HTLC} consumes the last \code{Route} fact, checks that $x$ hashes to~$y$,
emits \code{Redeemed(ptrIn,y)} and passes the preimage upstream as \code{Fulfilled(ptrIn,x)}.
The preimage is never sent over the network, and the adversary never learns it
(\code{Preimage_Never_Known}). \code{Intermediary_Settle} then consumes
\code{IntermediaryPending} and \code{Fulfilled(ptrOut,x)}, produces \code{Fulfilled(ptrIn,x)}
one hop upstream, and records \code{FeeEarned} when the intermediary collects its fee. Both
rules give the slot \code{Mutex(ptrIn)} back. \code{Sender_Settle} finally consumes
\code{SenderPending} and \code{Fulfilled(ptrSF,x)} and closes the payment with
\code{SenderSettled}.

Finally, the model lets a payment fail without punishment. \code{Open_Timeout} marks a channel
as timed out, and \code{Sender_Timeout_Refund} and \code{Intermediary_Timeout_Refund} consume
the corresponding pending state to return funds (recording \code{Refunded}). Both refund rules
also give the slot \code{Mutex} back. Timeouts are untimed channel events
(Sec.~\ref{sec:threat}): \code{Open_Timeout} may fire at any point once the channel exists, at
most once per channel (\code{OneTimeoutPerPtr}), and makes the pending HTLCs on that channel
refundable. The interplay of claiming and refunding is pinned down by the three restrictions of
Sec.~\ref{sec:restrictions}: T1 (\code{RedeemBeforeTimeout}) forbids redeeming after the
timeout, T2 (\code{OutgoingTimesOutFirst}) encodes the decreasing deadlines of
Remark~\ref{rmk:deadlines}, and T3 (\code{IntermediaryMustClaim}) encodes the claiming liveness
of Remarks~\ref{rmk:claiming} and~\ref{rmk:deadlines}.

\subsubsection{The Wormhole Rule}\label{sec:core-skip}
Besides the Dolev-Yao network and key compromise (\code{Compromise_Ltk}), the adversary has one
routing rule, used for the wormhole:
\begin{spthy}
rule AttackerSkip:
    [ Fulfilled(ptrExit, x),
      !RouteInfo(ExitAtt, Next, ptrExit, y)[-,no_precomp],
      !RouteInfo(EntryAtt, Skipped, ptrSkip, y)[-,no_precomp],
      !Compromised(ExitAtt),
      !Compromised(EntryAtt) ]
    --[ FulfilledProduced(ptrSkip, x),
        Skipped(ptrSkip, x),
        Eq(h(x), y) ]->
    [ Fulfilled(ptrSkip, x) ]
\end{spthy}
If two compromised parties, \code{ExitAtt} and \code{EntryAtt}, have each added an HTLC for the
same payment hash~$y$, on channels \code{ptrExit} and \code{ptrSkip}, then \code{AttackerSkip}
takes the preimage released on \code{ptrExit} and delivers it on \code{ptrSkip}.
\code{EntryAtt} can then settle upstream, while the hops between \code{ptrSkip} and
\code{ptrExit}, starting with \code{Skipped}, never see their outgoing HTLC fulfilled and can at
best be refunded. The rule emits \code{Skipped(ptrSkip,x)} but neither \code{Redeemed} nor
\code{FeeEarned}. It yields the wormhole trace of Sec.~\ref{sec:wormhole}
(\code{Wormhole_Fee_Theft_Reachable}), and the hop-bypass theorems
(Secs.~\ref{sec:wormhole} and~\ref{sec:bypass}) show that, if the sender settles, a forwarder at
positions 1 to 6 of the route, or at any position of a single-offer payment, is bypassed only if
some key was compromised.

\subsubsection{Amounts and Fees}\label{sec:core-amounts}
Amounts and fees are modelled per hop only. \code{Forward_HTLC} reads the incoming amount, the
fee and the outgoing amount from the network as natural-number terms and requires the incoming
amount to equal the outgoing amount plus the fee, so this balance holds at every hop by
construction. The three values are kept in \code{IntermediaryPending}.
\code{Sender_Offer_HTLC}, the invoice and the \code{Route} facts carry no amount, so amounts are
not chained along the path, and the model makes no statement about end-to-end value, such as
the amount the receiver obtains or the total fee the sender pays. We keep per-hop fees because
the wormhole of Sec.~\ref{sec:wormhole} is a fee theft. The fee is a single per-hop quantity
rather than Lightning's \texttt{base\_fee + fee\_rate} formula, and we prove nothing about fee
policy.

Fees are charged and earned by two separate events. \code{FeeCharged} is emitted when a
forwarder locks its outgoing HTLC; \code{FeeEarned} is emitted only when it later claims its
incoming one. In the wormhole trace, the bypassed honest hop emits \code{FeeCharged} but never
\code{FeeEarned}, although the sender settles and the receiver is paid
(\code{Wormhole_Fee_Theft_Reachable}, Sec.~\ref{sec:wormhole}). Conversely, a hop whose key is
never compromised earns a fee only after it has forwarded the payment and its outgoing HTLC has
been redeemed (\code{Fee_Only_On_Successful_Forward}).

We deliberately leave out three things. First, channel capacity: \code{Forward_HTLC} has no
\code{Wallet} premise and HTLCs do not change the balances in \code{StateA} and \code{StateB},
so a forward never fails for lack of funds. Second, concurrent HTLCs on one channel:
\code{Mutex(ptr)} is taken when an HTLC is added to channel \code{ptr} and given back when that
HTLC is redeemed or refunded, so a channel carries at most one pending HTLC at a time; later
payments can reuse it, each with a payment hash not used on that channel before (restriction
\code{OneHTLCPerHashPerChannel}). Third, onion routing: the sender chooses only the first hop,
each forwarder chooses its next hop among its own channels, and route information is kept in
local state rather than sent in layered encryption. We therefore make no claims about hiding who
pays whom, and the wormhole appears purely as fee theft, as also characterised
in~\cite{malavolta2019}. Similarly, \code{StateA} and \code{StateB} carry a state index and a
revocation secret, not the output structure of Fig.~\ref{fig:transaction}, and the two-stage
HTLC claim becomes a single transition. The second stage adds a CSV delay and a revocation path;
for the channel balance, these are captured by \code{Claim_Funds_A} (resp.\
\code{Claim_Funds_B}) and the punishment rules (Sec.~\ref{sec:structure}).

\code{lightning.spthy} is our main model. It contains the channel layer of
Sec.~\ref{sec:core-channels}, multi-hop routing with the single generic rule
\code{Forward_HTLC} (Sec.~\ref{sec:core-routing}) and the wormhole rule \code{AttackerSkip}
(Sec.~\ref{sec:core-skip}), all under one Dolev-Yao adversary that can compromise long-term
keys. In its default mode (\code{make verify}), all 55 lemmas are verified: 32 safety lemmas
about channels and payments (Secs.~\ref{sec:properties} to~\ref{sec:wormhole} and
Appendix~\ref{app:catalogue}); 13 lemmas (six theorems and seven helpers) showing that the
forwarders at positions 1 to 6 of a route cannot be bypassed unless some key was compromised
(Sec.~\ref{sec:bypass-fixed}); and 10 exists-trace lemmas. These show that the model is not
vacuous (channel updates, cooperative closes, refunds and honest multi-hop payments are
reachable), that the assumptions of our safety lemmas matter (a payment without a matching
invoice can settle once the receiver's key is compromised; a compromised intermediary can
lose), and that the wormhole is reachable. \code{make general} runs the same file without the
three liveness restrictions and proves the bypass theorem for routes of any length,
\code{Any_Hop_Skip_Requires_Compromise} (Sec.~\ref{sec:bypass-any}); since removing
restrictions only adds traces, this all-traces result also holds in the default mode.
\code{lightning_aux.spthy} holds five small, self-contained models, one per flag: the PTLC
countermeasure and its HTLC baseline (Sec.~\ref{sec:ptlc}), two timing models (block clock,
CLTV delta) that make explicit the deadlines the main model abstracts into untimed timeout
events, and the early-timeout race, the trace pattern that \code{Timeout_Race_Blocked} excludes
in the main model for uncompromised forwarders. \code{make necessity} removes one liveness
restriction at a time (Sec.~\ref{sec:timing}).

\paragraph{The Linear Single-Spend Discipline}\label{par:single-spend}
We enforce the no-double-spend rule using linear facts. As mentioned in
Sec.~\ref{sec:symbolic}, a persistent fact \texttt{!F()} is checked by a rule but not consumed,
whereas a linear fact \texttt{F()} is removed from the state when the rule fires. In our model
of the Lightning Network, the revocation secret is persistent knowledge
(\code{!RevokedSecret}), and the revoked commitment output is a linear one-shot token
(\code{RevokedCommitmentUnspent}), consumed when that state is published.

Initially, the punishment rule only needed one thing to trigger: the persistent revocation
secret alone. Our first \code{Publish_Revoked_A} had the premises of the rule below except the
last one, so every premise was persistent. Since punishment was gated only by
\code{!RevokedSecret}, the rule could fire again and again for the same revoked state: if a
party cheats, the honest party can take the channel funds many times. Lemmas like
\code{No_Punishment_Without_Cheating} still pass, because a cheat is still required. What they
miss is that punishment should happen only once. To fix this issue, we split the revoked state
into two separate facts: \code{Revoke_Old_Secret} (Sec.~\ref{sec:core-channels}) still stores
the secret as the persistent \code{!RevokedSecret}, and it also creates the linear token
\code{RevokedCommitmentUnspent}, for both parties. \code{Publish_Revoked_A} must consume that
token, so the same revoked commitment can be punished only once (\code{Publish_Revoked_B} is
symmetric):
\begin{spthy}
rule Publish_Revoked_A:
    [ !ChannelRecord(ptr, $A, $B),
      !ValidOnChain(ptr),
      !RevokedSecret($A, n_old, sAold, oldCommitA),
      RevokedCommitmentUnspent(ptr, $A, $B, n_old, oldCommitA) ]
    --[ PublishRevoked($A, n_old, oldCommitA),
        Cheat($A, n_old) ]->
    [ OnChainCheat($A, $B, n_old, oldCommitA),
      RevealedSecret($A, n_old, sAold, oldCommitA) ]
\end{spthy}
Persistent knowledge of the revocation secret is retained via \code{!RevokedSecret}. Only
spending the funds is linear.

We found the same critical flaw in our initial model of the routing layer. With the persistent
\code{!ChannelConnect} alone, one channel could add unboundedly many HTLCs on the same output.
We fixed it with a linear slot \code{Mutex(ptr)}. \code{Lock_Funds_And_Open} produces it once,
when the channel opens; \code{Sender_Offer_HTLC} and \code{Forward_HTLC} consume it when they
add an HTLC on that channel; \code{Receiver_Fulfill_HTLC}, \code{Intermediary_Settle},
\code{Sender_Timeout_Refund} and \code{Intermediary_Timeout_Refund} give it back when that HTLC
is redeemed or refunded. HTLCs are thus added to a channel one at a time, and the channel can be
reused once its HTLC has resolved.
\begin{spthy}
rule Lock_Funds_And_Open:
    [ ReadyToLock($A, $B, ptr, sA0, sB0, commitA0, commitB0),
      Wallet($A, ~fA), Wallet($B, ~fB) ]
    --[ ChannelOpen($A, $B, ptr), FundsLocked($A, $B, ptr),
        NewStateBuilt($A, $B, ptr, '0', ~fA, ~fB) ]->
    [ StateA($A, $B, ptr, '0', sA0, commitA0, ~fA, ~fB),
      StateB($A, $B, ptr, '0', sB0, commitB0, ~fA, ~fB),
      !ValidOnChain(ptr),
      !ChannelRecord(ptr, $A, $B),
      !ChannelConnect(ptr, $A, $B),
      !ChannelConnect(ptr, $B, $A),
      Mutex(ptr) ]
\end{spthy}
Adding a linear premise can remove some exists-trace witnesses. So we re-ran the whole of
\code{lightning.spthy} after both fixes: all 55 lemmas of \code{make verify} verify, including
the ten exists-trace lemmas (Table~\ref{tab:results}).
